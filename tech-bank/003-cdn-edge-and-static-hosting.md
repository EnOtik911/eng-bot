# 003 — CDN, edge и статический хостинг: Cloudflare, GitHub Pages, Netlify

> **Откуда вырос вопрос:** GATE 1, решение «Хостинг фронтенда»
> **Дата:** 2026-08-28

## Короткий ответ

**CDN** — сеть серверов по всему миру, каждый из которых отдаёт копию твоего файла.
Смысл не в надёжности и не в трафике, а в **latency**: скорость света конечна, и
запрос до Франкфурта из Москвы физически не может прийти быстрее, чем за десятки
миллисекунд. Копия рядом с пользователем убирает эту дистанцию.

Для Eng_bot CDN не нужен: один пользователь, один город. Поэтому выбор хостинга
решается не производительностью, а тем, где меньше движущихся частей — и это
GitHub Pages, потому что деплой уже происходит там, где лежит код.

## Как это работает

### Что делает CDN

Ты положил `app.js` в одно место. CDN раскладывает его копии по своим точкам
присутствия — **PoP**, points of presence — и направляет каждого пользователя
в ближайшую.

Направляет через **anycast**: один и тот же IP-адрес объявляется из сотен мест
одновременно, и маршрутизация интернета сама доставляет пакет в ближайшую точку.
Это не DNS-трюк и не редирект — пользователь не знает, что попал в другой город.

На точке присутствия происходит ещё две вещи, о которых обычно не думают:

- **TLS termination** — рукопожатие HTTPS выполняется здесь, а не на твоём сервере.
  Рукопожатие требует нескольких круговых обменов, и выполнить их за 5 мс вместо
  50 мс — это и есть основной вклад CDN в скорость первой загрузки.
- **Кэширование по заголовкам.** `Cache-Control` решает, сколько копия живёт.
  Забудешь его — получишь либо вечно устаревший файл, либо отсутствие кэша вовсе.

### Что такое edge и чем он отличается от serverless

**Edge computing** — выполнение кода на тех же точках присутствия, а не в одном
регионе. Cloudflare Workers, Deno Deploy, Vercel Edge Functions — это оно.

Отличие от обычного serverless вроде AWS Lambda не только в географии:

| | Обычный serverless | Edge |
|---|---|---|
| Где исполняется | один-два региона | сотни точек |
| Изоляция | контейнер или микро-ВМ | **V8 isolate** — как вкладка браузера |
| Cold start | сотни мс до секунд | единицы мс |
| Что доступно | почти весь Node/Python | ограниченный набор Web API, нет файловой системы |

**V8 isolate** — это ключ. Запуск контейнера дорог, запуск изолята в уже работающем
процессе V8 почти бесплатен. Отсюда почти отсутствующий **cold start** — и отсюда же
ограничения: нет своего процесса, нет диска, жёсткий лимит на CPU-время.

Для сравнения: Apps Script — наоборот, худший случай по обоим осям. Один регион и
задержка вызова 400–1500 мс. Именно поэтому в GATE 1 архитектура сложилась вокруг
буферизации в клиенте: не потому что так красиво, а потому что платформа медленная,
и единственный способ это скрыть — обращаться к ней два раза за сессию, а не сто.

### Три бесплатных тарифа, сверенные с документацией

| | GitHub Pages | Cloudflare Pages | Netlify |
|---|---|---|---|
| Трафик | **100 ГБ/мес** (soft) | не тарифицируется | **100 ГБ/мес** |
| Размер сайта | **1 ГБ** | — | — |
| Сборки | **10/час** (soft) | **500/мес** | **300 минут/мес** |
| Приватный репозиторий | нужен платный план | да | да |
| Функции на сервере | нет | Workers включены | Functions включены |

Важное: у GitHub Pages лимиты **есть**, и в GATE 1 я утверждал обратное — это была
ошибка, исправленная после проверки документации. «Soft» означает, что при превышении
не отключают мгновенно, а связываются и просят уехать. Для одного пользователя
100 ГБ в месяц недосягаемы: страница на сотню килобайт при десяти открытиях в день
даёт около 30 МБ в месяц — три тысячных лимита.

## Где ломается

- **Кэш не инвалидируется сам.** Обновил `app.js`, а браузер и CDN держат старый.
  Лечится **cache busting**: имя файла с хешем содержимого (`app.7f3a1c.js`) —
  новое содержимое даёт новое имя, старый кэш просто перестаёт быть нужным.
  Для Eng_bot достаточно проще: `?v=` с версией в URL.
- **Единственный регион у backend обнуляет выгоду CDN.** Статика приходит за 10 мс,
  а первый вызов API — за 800 мс. Оптимизировать статику дальше бессмысленно,
  узкое место не там. Это общий принцип: измеряй, потом оптимизируй.
- **Soft-лимит бесплатного тарифа — это не техника, а отношения.** Проект,
  который выстрелил, узнаёт о лимите из письма. Для личного инструмента риск нулевой,
  для чего-то публичного — нет.
- **GitHub Pages не отдаёт заголовки по твоему выбору.** Нельзя поставить
  свой `Content-Security-Policy` или `Cache-Control` — нет конфигурации сервера
  вообще. Cloudflare Pages умеет через файл `_headers`. Если однажды понадобится
  управлять заголовками — это будет причиной переезда, а не трафик.

## Почему у нас выбрано так

GitHub Pages, и причина одна: **деплой не добавляет нового места, где что-то может
сломаться**. Код уже в GitHub, значит публикация — это push, а не второй аккаунт,
второй набор токенов и второй дашборд, в который надо будет вспомнить, как войти.

Cloudflare Pages объективно щедрее: не тарифицирует трафик, даёт Workers и
позволяет приватный репозиторий бесплатно. Но каждое из этих преимуществ решает
проблему, которой у тебя нет.

Что переключит выбор:

- репозиторий должен стать приватным — GitHub Pages потребует платный план,
  Cloudflare нет;
- понадобятся свои HTTP-заголовки;
- понадобится серверная функция рядом со статикой — например, прокси к Apps Script,
  чтобы обойти ограничения CORS из записи [004](004-cors-and-same-origin.md).

Третий пункт стоит держать в голове: Cloudflare Worker в 20 строк снял бы жёсткое
правило «только простые запросы». Мы его не берём, потому что это ещё одна
платформа в стеке ради удобства, а не ради необходимости, — но это честная
альтернатива, а не тупик.

## Что потрогать руками

**Упражнение 1 — увидеть anycast (10 минут).**
```bash
# куда приходит запрос из твоей точки
curl -sI https://cloudflare.com | grep -i 'cf-ray\|server'
# трассировка: сколько прыжков до Cloudflare и сколько до Apps Script
traceroute cloudflare.com
traceroute script.google.com
```
`cf-ray` содержит код аэропорта той точки, которая тебя обслужила. Сравни число
прыжков в двух трассировках — это и есть физическая разница между edge и одним регионом.

**Упражнение 2 — измерить, где на самом деле время (15 минут).**
Открой любой сайт, DevTools → Network, посмотри разбивку одного запроса:
`Queueing`, `DNS`, `Initial connection`, `SSL`, `TTFB`, `Content Download`.
Найди, какая часть больше всех. Потом повтори на сайте без CDN. Различие будет
не в `Content Download`, а в `SSL` и `TTFB` — это и есть предмет разговора.
