# 004 — clasp и модель развёртывания Apps Script

> **Откуда вырос вопрос:** шаг 3 деплоя; «зачем терминал, если есть интерфейс Google»
> **Дата:** 2026-08-28

## Короткий ответ

Apps Script — это не «скрипты внутри таблицы». Это отдельная среда исполнения кода
на серверах Google, у которой есть свой редактор в браузере и свой API. **clasp** —
официальный CLI к этому API: он умеет создавать проект, заливать в него файлы и
забирать обратно.

Главная идея, которая объясняет всё остальное: у проекта Apps Script есть
**два независимых состояния** — код в редакторе и опубликованная версия. `clasp push`
меняет первое и не трогает второе. Пока не создана новая версия развёртывания,
внешний мир видит старый код. Это источник большинства потерянных часов.

## Как это работает

### Три сущности, которые легко спутать

| Сущность | Что это | Где живёт |
|---|---|---|
| **Script project** | Контейнер кода, у него есть `scriptId` | серверы Google |
| **Version** | Неизменяемый снимок кода, нумеруется 1, 2, 3… | там же |
| **Deployment** | Именованный указатель на конкретную версию, у него свой URL | там же |

`clasp push` заливает файлы в **project**. Ни version, ни deployment при этом не
создаются. Web App URL указывает на **deployment**, а тот — на **version**.
Отсюда правило: после каждой правки кода нужен новый version, иначе `/exec`
продолжает отдавать прежнее поведение.

Проверить, какой код реально работает, можно единственным честным способом —
дёрнуть живой endpoint, а не посмотреть в редактор.

### Что делает `clasp login`

Открывает OAuth-согласие в браузере и складывает токены в `~/.clasprc.json`
(домашний каталог, не репозиторий). Это твои личные учётные данные для
Apps Script API — файл нельзя коммитить и нельзя пересылать.

Флаг `-u, --user <name>` позволяет держать несколько наборов, если однажды
понадобится второй Google-аккаунт.

### Зачем включать «Google Apps Script API»

По умолчанию Google запрещает **программный** доступ к твоим скриптам — даже тебе
самому. Переключатель на
[script.google.com/home/usersettings](https://script.google.com/home/usersettings)
разрешает работу через API. Без него `clasp create` и `clasp push` отвечают ошибкой
с прямой ссылкой на эту страницу.

Это разумная защита: скрипты имеют доступ к твоей почте, диску и таблицам, и
включение API — осознанное действие, а не галочка по умолчанию.

### Что появляется локально

`clasp create` пишет в текущую папку файл `.clasp.json`:

```json
{ "scriptId": "1a2B...", "rootDir": "/путь/к/gas" }
```

- `scriptId` — адрес твоего проекта. Из него clasp понимает, куда пушить.
- `rootDir` — какую локальную папку считать корнем проекта.

`.clasp.json` в `.gitignore`, и это принципиально: он привязан к **твоему** личному
проекту. Если бы он лежал в репозитории, любой, кто склонировал репозиторий,
пушил бы в твой проект. Публичным остаётся код, приватным — адрес.

Учётные данные (`~/.clasprc.json`) и адрес проекта (`.clasp.json`) — разные файлы
в разных местах, и путать их не надо: первый про «кто ты», второй про «куда».

### Как файлы отображаются на удалённый проект

`clasp push` берёт из `rootDir` все файлы поддерживаемых типов и заливает их
с сохранением имён:

| Локально | В редакторе Apps Script |
|---|---|
| `Fsrs.gs` | файл `Fsrs.gs`, тип «Script» |
| `appsscript.json` | манифест проекта |
| `*.html` | файл типа «HTML» |

Всё остальное игнорируется. Флаг `-f` (`--force`) отключает вопрос
«точно перезаписать удалённые файлы?» — нужен, чтобы команда не требовала ответа.

**Порядок файлов не важен для функций.** Apps Script загружает все файлы в одну
глобальную область видимости, а объявления функций поднимаются (hoisting), поэтому
`Main.gs` может вызывать функцию из `Fsrs.gs` независимо от порядка. Значение имеет
только порядок выполнения кода на верхнем уровне — присваиваний вне функций.
У нас такие есть (`var FSRS_DEFAULT_W = [...]`), но они только читаются внутри
функций, то есть к моменту первого чтения уже вычислены.

Поэтому одиннадцать файлов и один склеенный ведут себя одинаково. Одиннадцать —
не красивее, а дешевле в поддержке: правку видно в diff, а не в куске из 1248 строк.

### Что такое `--type standalone`

Проект Apps Script бывает **привязанным** к документу (bound) или **отдельным**
(standalone).

- Bound живёт внутри конкретной таблицы, доступен через «Расширения → Apps Script»,
  умеет `SpreadsheetApp.getActiveSpreadsheet()` и погибает вместе с документом.
- Standalone — самостоятельный объект на Google Диске. К таблице обращается по id
  через `SpreadsheetApp.openById()`.

Мы берём standalone по трём причинам: код не привязан к судьбе одного документа,
таблицу можно заменить правкой одного свойства, а источником истины остаётся
репозиторий, а не документ.

## Где ломается

- **`clasp push` без нового version.** Самая частая потеря времени. Симптом:
  правку видно в редакторе, `/exec` ведёт себя по-старому.
- **`clasp create` в папке, где уже есть `.clasp.json`.** Отказывается, чтобы не
  потерять привязку. Если проект действительно нужен новый — удали `.clasp.json`.
- **Запуск не из той папки.** `clasp push` из корня репозитория зальёт не то,
  что ожидаешь: `rootDir` берётся из `.clasp.json`, а сам файл ищется в текущей
  папке и выше.
- **`clasp pull` затягивает удалённые файлы поверх локальных.** Если правил код в
  браузере, а потом сделал `push` — правки в браузере потеряны. Направление надо
  выбрать и держаться: у нас источник истины — репозиторий, значит `push`.
- **Глобальная установка через `npm i -g`** часто кладёт бинарник вне `PATH`,
  и получается `command not found: clasp` при формально успешной установке.
  `npx` этой проблемы не имеет: он запускает пакет из кеша, не полагаясь на `PATH`.
- **Команды переименованы в 3.x.** `clasp open` стал `clasp open-script`,
  `clasp deploy` — `clasp create-deployment`. Старые статьи в интернете дают
  команды 2.x, и они молча не находятся.

## Почему у нас выбрано так

Терминал здесь не про удобство, а про то, где живёт истина. Если код правится в
браузере, репозиторий превращается в устаревшую копию, ADR перестают соответствовать
коду, а тесты проверяют не то, что исполняется. `clasp push` делает направление
однонаправленным: правка → коммит → пуш.

Браузерный путь оставлен как аварийный выход, но с ценой, которая названа вслух:
следующая правка потребует ручного копирования.

## Что потрогать руками

**Упражнение 1 — увидеть разрыв между кодом и развёртыванием (10 минут).**
После того как всё заработает: измени в `Bot.gs` текст ежедневного пинга,
сделай `clasp push -f`, и **не** создавая новую версию, дёрни живой endpoint.
Убедись, что поведение прежнее. Потом создай версию и повтори. Это то самое
различие, из-за которого «я же поправил» и «на проде старое» уживаются вместе.

**Упражнение 2 — посмотреть, что именно уйдёт (2 минуты).**
```bash
cd gas
clasp show-file-status     # он же clasp status
```
Печатает список файлов, которые попадут в push, и список игнорируемых.
Полезно перед первым пушем: сразу видно, если запустил не из той папки.

**Упражнение 3 — прочитать логи не выходя из терминала (5 минут).**
```bash
clasp tail-logs --watch
```
Показывает `Logger.log` из выполнений, включая триггеры. Это единственный способ
увидеть, что делал `dailyPing` в 8 утра, не открывая браузер.
