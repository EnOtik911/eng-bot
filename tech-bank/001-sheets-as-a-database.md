# 001 — Google Sheets как база данных: что это на самом деле и где ломается

> **Откуда вырос вопрос:** GATE 1, строка таблицы решений «Хранилище»
> **Дата:** 2026-08-28

## Короткий ответ

Google Sheets — это не база данных, а документ с табличным интерфейсом. У него нет
ничего из того, за что платят базам: ни **transactions**, ни **indexes**, ни
**constraints**, ни **types**. Есть только сетка ячеек и API, который её читает
и пишет целыми диапазонами.

Для Eng_bot этого достаточно, и не потому что «на маленьких проектах можно
халтурить», а потому что у нас ровно один **writer** и объём данных на два порядка
ниже границы, где Sheets начинает деградировать. Как только появится второй
одновременный писатель или сотня тысяч строк — выбор перестанет быть верным.

## Как это работает

**Модель хранения.** Таблица — это XML/JSON-документ в Google Drive, а не набор
страниц на диске с B-деревьями поверх. Когда ты пишешь в ячейку, Google не находит
её по индексу — он применяет операцию к документу целиком и пересчитывает всё, что
от неё зависит (формулы, условное форматирование, сводные таблицы). Отсюда все
свойства, которые дальше.

**Доступ из Apps Script.** Каждый вызов `getValue()` или `setValue()` — это
отдельный сетевой запрос к серверу Sheets. Не «немного медленнее», а на два порядка:
цикл с последовательными записями по ячейке выполняется около 70 секунд там, где
пакетная версия того же кода — около 1 секунды. Поэтому единственный правильный
паттерн — читать и писать диапазонами:

```javascript
// плохо: 100 сетевых запросов
for (var i = 0; i < 100; i++) {
  sheet.getRange(i + 2, 5).setValue(newDue[i]);
}

// хорошо: 1 сетевой запрос
var column = newDue.map(function (v) { return [v]; });   // 2D-массив, обязательно
sheet.getRange(2, 5, column.length, 1).setValues(column);
```

`getValues()` возвращает **2D array** — массив строк, каждая строка массив ячеек.
`setValues()` требует такой же формы, и размер диапазона должен совпадать с размером
массива ровно, иначе исключение. Это первое, обо что все спотыкаются.

**Отсутствие транзакций.** В базе `BEGIN … COMMIT` гарантирует, что либо применились
все изменения, либо ни одно. В Sheets такого нет вообще. Если скрипт упал после
записи 40 строк из 100 — в таблице лежат 40 строк, и никто их не откатит. Поэтому
в спеке Eng_bot появились две вещи, которые в проекте на Postgres были бы лишними:
`source_batch` в карточках (чтобы можно было удалить незавершённую загрузку целиком
по метке) и `flush_log` с `batch_id` (чтобы повторная отправка той же пачки
распознавалась и отбрасывалась — это и есть **idempotency**).

**Отсутствие блокировок на уровне данных.** База умеет заблокировать строку, пока
её кто-то меняет. Sheets — нет: две записи в одну ячейку просто перезатрут друг
друга, и последняя победит. Это **race condition**, и её видно не сразу, а как
«иногда пропадают оценки». Лечится снаружи, через `LockService` Apps Script — это
**mutex**, взаимное исключение: пока один скрипт держит замок, второй ждёт.

```javascript
var lock = LockService.getScriptLock();
if (!lock.tryLock(30000)) throw new Error('LOCKED');
try {
  // только запись, ничего больше
  sheet.getRange(2, 1, rows.length, rows[0].length).setValues(rows);
} finally {
  lock.releaseLock();          // finally обязателен, иначе замок повиснет до таймаута
}
```

Важное правило: чтение, вычисления и сборка результата — **вне** замка. Внутри
только запись. Замок на всю функцию блокирует лишнее и превращает «защиту от гонки»
в «узкое место».

**Отсутствие типов и ограничений.** Колонка `due` — это не `DATE NOT NULL`, это
просто ячейки, куда можно положить что угодно, включая строку «завтра» и пустоту.
База отвергла бы такое на входе; Sheets примет и отдаст обратно. Поэтому вся
валидация переезжает в код (`Import.gs` в нашей спеке), и это не перестраховка,
а обязанность, которую сняли с хранилища.

Отдельная ловушка: Sheets сам приводит типы при вводе. Строка `1-2` может стать
датой, а `+7...` — формулой. При записи через API этого не происходит, но при
вставке батча руками в лист `inbox` — происходит. Поэтому формат импорта у нас
TSV с текстовыми колонками, а не «вставь как получится».

## Где ломается

Числа, а не ощущения:

| Порог | Что происходит |
|---|---|
| **10 000 строк** | Ниже этого — быстро. Это рабочая зона. |
| **~100 000 строк** | Заметная деградация: пересчёт и отклик API растут. |
| **10 000 000 ячеек** | Жёсткий лимит на всю таблицу, включая все листы. При 18 колонках это около 555 000 строк суммарно. |
| **6 минут** | Лимит одного исполнения Apps Script на личном аккаунте. Долгая пакетная операция упадёт по таймауту на середине — см. отсутствие транзакций выше. |

Прогноз для Eng_bot при норме 6 новых слов в день:

- `cards`: 6 слов × 2 направления × 365 ≈ **4 400 строк в год** — с запасом ниже 10 000.
- `review_log`: ~100 повторений в день ≈ **36 500 строк в год** — вот это упрётся.

Отсюда решение в спеке: журнал живёт отдельным листом с ротацией по годам, и
планировщик его **не читает никогда** — состояние FSRS хранится в строке карточки.
Это ключевой приём: если растущая таблица не участвует в горячем пути, её рост
перестаёт быть архитектурной проблемой и становится вопросом уборки.

## Почему у нас выбрано так

Три ограничения делают выбор, и все три — твои:

1. **Ноль постоянных затрат.** Sheets бесплатны без карты. Managed Postgres — нет,
   а бесплатные тиры баз имеют привычку засыпать или исчезать.
2. **Никаких своих серверов.** Хранилище должно быть чужой заботой.
3. **У тебя есть продакшн-опыт этого стека.** Это не сентиментальность:
   знакомый инструмент экономит именно то время, которого в проекте меньше всего.

Плюс одно свойство, которое база как раз бы отняла: **ты видишь свои данные и можешь
их править руками**. Ты бросил Anki в том числе потому, что базой нельзя было
управлять. Здесь база — открытая таблица.

Что сняло бы этот выбор: второй одновременный писатель (появится, если раздашь бота
знакомым и они начнут заниматься параллельно), либо переход `cards` через ~50 000
строк, либо потребность в запросах со соединениями и агрегатами по журналу.

## Что потрогать руками

**Упражнение 1 — увидеть цену вызова (10 минут).**
Создай пустую таблицу, открой Apps Script и выполни:

```javascript
function benchmark() {
  var sh = SpreadsheetApp.getActiveSheet();
  var t1 = Date.now();
  for (var i = 1; i <= 200; i++) sh.getRange(i, 1).setValue(i);
  var slow = Date.now() - t1;

  var rows = [];
  for (var j = 1; j <= 200; j++) rows.push([j]);
  var t2 = Date.now();
  sh.getRange(1, 2, 200, 1).setValues(rows);
  var fast = Date.now() - t2;

  Logger.log('по ячейке: ' + slow + ' мс, пакетом: ' + fast + ' мс, разница ×' + Math.round(slow / fast));
}
```

Запиши результат сюда, в раздел «что изменилось потом». Это число стоит помнить
наизусть — оно объясняет половину решений в спеке.

**Упражнение 2 — поймать гонку (15 минут).**
Напиши функцию, которая читает число из `A1`, ждёт секунду через `Utilities.sleep(1000)`,
прибавляет единицу и записывает обратно. Запусти её из двух вкладок редактора почти
одновременно. Ожидаемо: `A1` вырос на 1, а не на 2 — одно обновление потерялось.
Потом оберни в `LockService` как выше и повтори. Это **lost update**, самый частый
баг конкурентного доступа, и ты только что воспроизвёл его на двадцати строках кода.
